# 🔥 شعله باشی (Sholeh Bashi)

اپلیکیشن اندروید برای **پیشنهاد غذا و دستور پخت**. کاربر سلیقه، رژیم و شرایطش را مشخص می‌کند و اپ سه غذای مناسب پیشنهاد می‌دهد. حس اپ باید «وارد شدن به آشپزخانه» باشد: گرم، زیبا، روان و سبک.

> این فایل برای همه‌ی کسانی است که وارد پروژه می‌شوند: اول بخوانید اپ چیست، بعد بخش «چطور ادامه بدهیم» را ببینید.

---

## ۱. اهداف و اصول

| اصل | معنی در عمل |
|---|---|
| مصرف باتری حداقل، بدون گرم شدن گوشی | هیچ سرویس پس‌زمینه یا Polling نیست. API فقط با اقدام کاربر صدا زده می‌شود. انیمیشن‌ها سبک‌اند. |
| زیبایی و حس آشپزخانه | پالت گرم، انیمیشن روان بین صفحه‌ها، Lottie سبک. |
| ریسپانسیو | Jetpack Compose + Material 3؛ باید روی اندازه‌های مختلف گوشی تست شود. |
| Local-first | دیتابیس روی گوشی (Room). اپ بدون اینترنت هم غذاهای خودی را نشان می‌دهد. |
| امنیت کلید API | کلید Gemini و Grok **هرگز** داخل APK نمی‌ماند؛ فقط روی سرور واسط است. |
| انتشار محدود | فعلاً فقط روی چند گوشی؛ دسترسی API با شناسه‌ی دستگاه کنترل می‌شود. |

## ۲. تکنولوژی‌ها

- **Kotlin + Jetpack Compose** (Material 3)، حداقل SDK ۲۴
- **Room** برای دیتابیس لوکال، **DataStore** برای تنظیمات
- **Retrofit + kotlinx.serialization** برای ارتباط با سرور واسط
- **Navigation Compose** با انیمیشن انتقال
- **Lottie** (انیمیشن سبک)، **Coil** (عکس)
- **سرور واسط** (پیشنهاد: Cloudflare Workers، خارج از ایران) که به Gemini و Grok وصل می‌شود

## ۳. صفحه‌ها و ویژگی‌ها

### دیالوگ خوش‌آمد
در اولین ورود، پنجره‌ای خوش‌آمد می‌گوید و کار اپ را توضیح می‌دهد. گزینه‌ی «بستن» و «دیگر نشان نده» دارد (ذخیره در DataStore با کلید `hide_welcome`).

### صفحه‌ی اصلی (۵ گزینه)

**۱. غذای رندوم**
- یک غذا به‌صورت تصادفی از دیتابیس نشان می‌دهد.
- دیتابیس شامل غذاهای سازنده (هزار غذا با دستور پخت، که با آپدیت‌ها بیشتر می‌شود) و غذاهای اضافه‌شده توسط کاربر است.
- کاربر می‌تواند غذا اضافه کند.
- نشان‌گذاری: «محبوب» و «برای پختن در آینده».

**۲. غذای جدید (با API)**
کاربر خواسته‌اش را مشخص می‌کند، سپس **سه غذا** پیشنهاد می‌شود. گزینه‌ها:
1. **می‌خواهم داشته باشد** (مثلاً برنج): کاربر دستی می‌نویسد. موارد ثبت‌شده در دیتابیس ذخیره می‌شوند و دفعه‌ی بعد زیر کادر نوشتن به‌صورت پیشنهاد (Suggest) می‌آیند تا بتواند دوباره اضافه کند یا اشتباه‌ها را حذف کند.
2. **نمی‌خواهم داشته باشد** (مثلاً خیار): دقیقاً مثل گزینه‌ی ۱.
3. **المان‌های مهم**:
   - بدنسازی (افزایش حجم)
   - کاهش وزن
   - حساسیت‌ها (ثبت، Suggest و حذف مثل بالا)
   - رژیم خاص (کاربر می‌نویسد؛ ثبت، Suggest و حذف مثل بالا)
4. **دلت چی می‌خواد؟** توضیح تکمیلی آزاد.
5. **تعیین وعده:** صبحانه، ناهار، شام، عصرانه، دسر، سالاد و ...
6. **کشور/منطقه:** ایران، عربی، ترکی، شرق آسیا، بقیه‌ی آسیا، اروپا، قاره‌ی آمریکا (شمالی و جنوبی)، آفریقا.

خروجی: سه غذا، با قابلیت نشان‌گذاری (محبوب / آینده).

**۳. غذاهای قبلی:** غذاهایی که کاربر تایید کرده است.
**۴. نشان‌شده‌ها:** هم «پسند شده‌ها» و هم «برای آینده».
**۵. درباره‌ی ما:** معرفی اپ، نسخه، و آیدی تلگرام سازنده.

## ۴. معماری

```
app/src/main/java/com/sholehbashi/app/
├── MainActivity.kt
├── navigation/        ناوبری و انیمیشن انتقال
├── ui/
│   ├── theme/         رنگ‌ها، فونت و تم آشپزخانه
│   ├── welcome/       دیالوگ خوش‌آمد
│   ├── home/          صفحه‌ی اصلی
│   ├── random/        غذای رندوم
│   ├── newmeal/       غذای جدید (فرم و نتیجه)
│   ├── history/       غذاهای قبلی
│   ├── saved/         نشان‌شده‌ها
│   └── about/         درباره‌ی ما
├── data/
│   ├── db/            Room (Entity, DAO, Database)
│   ├── prefs/         DataStore
│   ├── api/           Retrofit و مدل‌های درخواست/پاسخ
│   └── repo/          Repository ها
└── util/DeviceId.kt   شناسه‌ی یکتای نصب
```

### جدول‌های Room
- `recipes`: غذاها (`source` = `builtin` | `remote` | `user` | `ai`؛ غذاهای `ai` پیشنهادهای API هستند که کاربر نشان‌دار یا تایید کرده)
- `meal_marks`: نشان‌ها (`FAVORITE` | `COOK_LATER`) برای هر غذا
- `history`: غذاهای تاییدشده
- `user_prefs`: خواسته‌های ثبت‌شده (`type` = `WANT` | `AVOID` | `ALLERGY` | `DIET`، و `value`)

## ۵. دیتابیس غذاها و آپدیت‌ها

1. نسخه‌ی اول: دیتابیس آماده داخل APK (`assets/recipes.db`) و بارگذاری با `createFromAsset`.
2. آپدیت‌های بعدی: فایل JSON روی سرور با شماره‌ی نسخه. اپ هنگام باز شدن فقط نسخه را چک می‌کند و در صورت جدید بودن، تفاوت را در Room ادغام می‌کند.
3. غذاهای کاربر (`source=user`) هرگز پاک یا بازنویسی نمی‌شوند.

## ۶. امنیت و محدودسازی دستگاه‌ها

```
اپ ──(Device ID + کد دعوت)──► سرور واسط ──► Gemini / Grok
```

- اپ در اولین اجرا یک UUID می‌سازد و با هر درخواست می‌فرستد (به‌همراه مدل گوشی و نسخه‌ی اندروید).
- سرور یک **Allowlist** دارد: دستگاه ناشناس بلاک می‌شود. اگر اپ لو برود، شناسه‌ی مشکوک حذف می‌شود.
- سرور Rate Limit دارد و می‌تواند بین Gemini و Grok جابجا شود.
- از روی همین ثبت‌نام می‌شود دید چه گوشی‌هایی استفاده می‌کنند. (در «درباره‌ی ما» شفاف بنویسید چه اطلاعاتی ثبت می‌شود.)
- API های Gemini و Grok برای IP ایران بسته‌اند؛ سرور واسط باید خارج از ایران باشد.
- فعلاً به سرویس‌های گوگل (Firebase / Play Integrity) وابسته نشده‌ایم چون برای کاربران ایران قابل اتکا نیست.

## ۷. وضعیت فعلی

✅ اسکلت پروژه، تم، ناوبری با انیمیشن، Room، DataStore، دیالوگ خوش‌آمد، هر ۵ صفحه (نسخه‌ی اولیه)، فرم کامل «غذای جدید» با ثبت/Suggest/حذف، لایه‌ی API (قرارداد)
✅ سرور واسط (پوشه‌ی `server/`): Cloudflare Worker + D1، ثبت و تایید دستگاه‌ها، سقف روزانه، Gemini با fallback به Grok (راه‌اندازی در `server/README.md`)
⬜ هنوز انجام نشده: دیپلوی سرور و گذاشتن آدرسش در اپ، پر کردن دیتابیس غذاها (فعلاً ۳ غذای نمونه)، آپدیت دیتابیس از سرور، فونت فارسی، آیکون اپ، انیمیشن‌های Lottie، تست روی گوشی‌های مختلف

> ⚠️ این اسکلت هنوز در Android Studio کامپایل و اجرا نشده است. اولین Sync/Build ممکن است نیاز به رفع خطاهای کوچک یا به‌روزرسانی نسخه‌ها داشته باشد. فایل Gradle Wrapper هم داخل پروژه نیست؛ Android Studio خودش آن را می‌سازد.

## ۸. چطور ادامه بدهیم

1. پروژه را با **Android Studio** باز کنید و Gradle Sync بزنید (در صورت نیاز نسخه‌ها را در `gradle/libs.versions.toml` به‌روز کنید).
2. در `data/api/ApiConfig.kt` آدرس سرور واسط را بگذارید (فعلاً نمونه است).
3. ترتیب پیشنهادی کار:
   1. دیپلوی سرور واسط (کد آماده در `server/`؛ مراحل در `server/README.md`)
   2. ساخت `assets/recipes.db` و ثبت هزار غذا (ساختار در `RecipeEntity`)
   3. تکمیل فرم «غذای جدید» (Suggest و حذف برای موارد ثبت‌شده)
   4. افزودن غذای دستی توسط کاربر
   5. آپدیت دیتابیس از سرور
   6. طراحی نهایی، انیمیشن‌ها و تست باتری (Battery Historian / Profiler)
4. متن‌های فارسی صفحه‌های داخلی (فرم غذای جدید و ...) فعلاً داخل کد هستند؛ بهتر است به `strings.xml` منتقل شوند.
5. هر قابلیت جدید را با شاخه‌ی جدا (branch) توسعه دهید و قبل از ادغام، روی حداقل یک گوشی کم‌قدرت تست کنید.
